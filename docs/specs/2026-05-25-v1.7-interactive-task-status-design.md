# Blik Plan v1.7 — Interactive Task Status (Design Spec)

> **Source of truth** for the v1.7 feature set. Plans 1–4 implement against this spec. The original brainstorming session memory lives at `~/.claude/projects/-Users-cncuser/memory/reference_blikplan_v1_7_plan.md`.

## Goal

Turn the Gantt from a static plan into a live schedule that breathes with reality. Tasks gain an actionable status (Done / On Track / Not Started / Late). Bar fill colour communicates status. Phase identity moves off the bar onto a pastel row band. A nightly tick narrows Not Started bars and extends Late bars, rippling downstream where the per-job setting allows. A 6am Morning Inbox catches anything you forgot to mark Done.

## Statuses (4)

Bar fill = status. No emojis. Labels stay literal so they translate cleanly; humour, if added, lives in the inbox copy.

| Status | Label | Colour | Token | Bar behaviour |
|---|---|---|---|---|
| Done | "Done" | Green | `--status-done` `#10B981` | Truncates to completion date |
| On Track | "On Track" | Blue | `--status-ontrack` `#3B82F6` | Unchanged |
| Not Started | "Not Started" | Amber | `--status-notstarted` `#F59E0B` | Narrows daily from the left (start = today, end locked); flips to Late if today passes end date |
| Late | "Late" | Red | `--status-late` `#DC2626` | Extends daily from the right until marked Done |

Default status on task creation: **On Track**.

## Ripple rules

- **Done** → bar truncates to actual completion date. If `auto_shift_dependents` ON for the job, downstream dependents **pull in** (move earlier). This requires a new **upstream-symmetric** ripple — the existing `compute_ripple` is downstream-only.
- **On Track** → no schedule change.
- **Not Started** → at each midnight tick, `start_date` moves to today; `end_date` (derived from start + duration) stays locked, which means `duration_workdays` is recomputed downward. No downstream ripple (end date unchanged).
- **Late** → at each midnight tick, `duration_workdays += 1` (extends end by one workday). If `auto_shift_dependents` ON, downstream dependents push out.

## Per-job setting

`auto_shift_dependents: bool` — stored on the `job` row, default `true`. Settable from JobDetails. Some jobs (research, exploratory) want it OFF so dependent dates don't move around when reality shifts.

## Mark Done UX

- Default completion date = **yesterday** (you usually update the morning after).
- Date picker available when "Pick date…" is chosen.
- Exception: if a task was marked Late and is now being marked Done, default completion date = **today** (it's been ongoing).

## Morning Inbox (6am local time)

Daily at 6am device-local time: any task whose planned end date was yesterday and is not yet marked Done generates an inbox item.

- Native push notification (via `tauri-plugin-notification`) + in-app inbox panel (persists till cleared).
- One-tap actions per item: **Done yesterday** / **Still going** / **Pick date…**
- "Still going" flips the task to **Late** and starts the daily extension cycle.
- Items are stored as a new `morning_inbox_item` `PatchOp` type and render in the existing `InboxPanel` alongside Claude proposals.

## Visual design

### Bar fill = status
Bar fill is driven entirely by `task.status` (with a fallback to `phase.colour` only if status is somehow unset, which shouldn't happen after migration).

### Hover state
Hovering a bar darkens it (CSS `:hover` on the rect) and shows a custom tooltip with:
- Status label
- Planned vs actual dates
- Days slipped (if Late)
- Dependent task count

Uses a new `Tooltip.svelte` component (the codebase currently uses native `title=""` only; not rich enough for this).

### Phase identity = pastel row band
Each phase gets a faint pastel background band running the full timeline width, behind all its child rows. Bars sit on top.

- **Default**: auto-assigned from a fixed 6-colour cool/neutral pastel palette, cycling by `phase.order_index` modulo 6.
- **Override**: user can pick a hex via a colour picker in PhaseDetails (or right-click → "Set colour…").
- **Storage**: the existing `phase.colour` field becomes the override slot. Migration interpretation: if a phase has the legacy default hex string (`#3B82F6` or similar), treat it as "auto"; otherwise treat as user override. _Implementation detail to confirm in Plan 3 — may instead add a nullable `phase.color_override` and keep `phase.colour` purely as a render hint._
- **Layering**: pastel band sits **under** the past-task fade overlay (which is `fill-opacity` on the bar rect itself), so faded past bars correctly reveal the band.

### Phase-level red rollup
- Phase row goes **red** only if any child task is **Late**. (Worst-child wins, but only Late triggers it.)
- Otherwise the phase keeps its normal appearance.
- **Not Started** never affects phase appearance — Not Started before its planned start is normal, after its end it auto-flips to Late which then triggers the rollup.

## Open questions — RESOLVED

1. **Done tasks fading over time?** → **No.** Solid green for v1.7. The past-task fade overlay (v1.3) already provides a temporal cue; layering both is visual noise.
2. **Milestones (zero-duration tasks)?** → **Same 4 statuses**, with the narrow/extend mechanics degenerating sensibly: a Late milestone slides its date forward each midnight tick; a Not Started milestone snaps to today each tick. Done milestones snap to their completion date.
3. **Recurring tasks?** → **Out of scope for v1.7.** Punted to a future version. No data-model concession in this version.
4. **6am tick when device travels timezones?** → **Device-local time**, recomputed each day from `chrono::Local::now()`. No special handling. If you fly east and miss your 6am, tough — the next day's inbox catches it.

## Plan split

The work splits into 4 sequential plans, each shippable in isolation:

| Plan | Scope | User-visible? |
|---|---|---|
| **Plan 1: Foundation** | Data model, migration, repo, IPC, TaskStatus enum. No UI behaviour change. | No |
| **Plan 2: Status visualisation** | Status-driven bar colours, status UI (context menu + TaskDetails selector), hover tooltip, phase-red-on-Late rollup. | Yes — users can set status and see colour changes |
| **Plan 3: Pastel phase bands** | DOM restructure, auto palette, per-phase override picker. | Yes — phase visual identity moves to row bands |
| **Plan 4: Scheduling + automation** | Upstream ripple, midnight tick, 6am Morning Inbox, native push notifications, per-job auto-shift toggle. | Yes — schedule starts moving on its own |

Plans 1 and 2 give the user a complete manual-status experience. Plans 3–4 add the polish and automation.

## Out of scope

- Recurring tasks
- Done tasks fading over time
- Status-history audit log (who marked what when)
- Bulk-status operations
- Status-filter views ("show me all my Late tasks across all jobs")
- Mobile-specific UI (Tauri desktop only for now)
