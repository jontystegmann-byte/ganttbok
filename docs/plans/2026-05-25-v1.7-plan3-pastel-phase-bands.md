# Blik Plan v1.7 — Plan 3: Pastel Phase Bands (OUTLINE)

> **Status:** Outline only. Flesh out before execution.

**Goal:** Replace per-bar phase colouring with a faint pastel **row band** behind each phase's tasks. Defaults to an auto-assigned palette; per-phase override available.

**Spec:** `docs/specs/2026-05-25-v1.7-interactive-task-status-design.md`

**Depends on:** Plan 2 (status now drives bar fill, so phase identity is free to move).

---

## Design decision to resolve at the top of this plan

The spec leaves this open: **should `phase.colour` become the override-only slot, or do we add `phase.color_override: Option<String>` and treat `phase.colour` as the render-time resolved value?**

- **Option A (simpler):** Repurpose `phase.colour` as override-only. If the value matches a known auto-palette entry (or a sentinel like the empty string), treat as "auto". Migration: leave existing values alone — they become explicit overrides, which is fine because they were chosen-or-defaulted at job-creation time anyway. Pro: no schema change. Con: muddies the meaning of the field.
- **Option B (cleaner):** Add `phase.color_override: Option<String>`. `phase.colour` is dropped or kept as a legacy field. Migration: set `color_override = NULL` for all rows. Pro: explicit semantics. Con: another migration.

**Recommendation: Option A.** Lower migration risk; the field's meaning becomes "override or null". UI logic: if the value equals the auto-assigned colour for that phase's `order_index`, show "Auto" in the picker; otherwise show the override.

(If users have already customised many phases via the existing colour picker, those become real overrides — which is what they wanted anyway.)

## Key task steps

1. **Resolve the schema decision** (Option A or B above). Document choice at top of the implementation.
2. **CSS tokens** — six cool/neutral pastels (avoid red so it doesn't compete with `--status-late`).
3. **`pastelForIndex` helper** + unit test.
4. **`PhaseBand.svelte`** — props: `top`, `height`, `colour`; absolute-positioned with `width: 100%`, `z-index: 0`, no pointer events.
5. **Wire bands into `GanttCanvas`** — for each phase in `store.phases`, compute its row span. Render bands BEFORE the SVG.
6. **Strip phase colour from bars** — remove any remaining `phase.colour` references in `TaskBar.svelte`.
7. **PhaseDetails colour picker** — "Auto" radio + hex override. Saving "Auto" sends `setPhaseColor(id, null)`.
8. **Backend command + repo update** — `set_phase_color` writes null or a hex string. Update `phase.colour` SELECT/UPDATE if Option A; otherwise add new column.
9. **Confirm layering** — past-task fade (bar `fill-opacity`) shows the band through faded bars. Today-line stays above bands but below tooltips.

## Acceptance criteria

- A fresh job's phases get distinct pastel bands cycling through the 6-colour palette by phase order.
- Past tasks visibly fade against the pastel band (band shows through).
- Picking a custom hex in PhaseDetails replaces the auto colour; choosing "Auto" reverts.
- Bars are coloured only by status — no phase identity on the bar itself.
- Today-line still draws on top of bands and bars.

## Anti-pattern guards

- Bands MUST sit at z-index 0 (or behind the SVG). The SVG must NOT have an opaque background — confirm `svg { background: transparent; }`.
- Do NOT add phase-band rendering inside the SVG; keep it as a separate DOM div so CSS variables work naturally.
- Do NOT use saturated colours for the palette — pastels must let warm status colours (amber/red) pop.
